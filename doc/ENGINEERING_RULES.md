# 개발 규칙

이 문서는 `idleGame` 프로젝트 작업 기준이다. 기능을 빠르게 붙이는 것보다 다음 기능을 붙여도 무너지지 않는 구조를 우선한다.

## 1. 기본 원칙

- 새 기능은 먼저 책임 위치를 정한다. `View`, `State`, `Service`, `Definition`, `Manager` 중 어디가 맞는지 선택하고, 필요하면 구현 전에 분리 기준을 정한다.
- 거대 클래스에 새 기능을 직접 추가하지 않는다.
- 리팩토링 커밋에는 동작 변경을 섞지 않는다.
- 기능 커밋에는 대규모 파일 이동을 섞지 않는다.
- 임시 구현은 가능하지만, 임시임을 문서와 코드 구조에 남긴다.

## 2. 폴더와 네임스페이스

- namespace는 폴더 구조와 맞춘다.
- 파일 하나에는 public class 하나를 둔다.
- 파일명은 대표 class명과 같게 둔다.
- Unity가 생성한 `.meta` 파일은 스크립트 이동 시 같이 이동한다.

예:

```text
Assets/Scripts/UI/Hero/Formation/HeroFormationView.cs
namespace IdleGame.UI.Hero.Formation
```

## 3. 클래스 크기 기준

- 300줄 초과: 분리 후보.
- 500줄 초과: 경고. 새 기능 추가 전에 분리 검토.
- 800줄 초과: 신규 기능 추가 금지. 먼저 분리한다.
- 메서드 60줄 초과: 작은 메서드로 나눌 수 있는지 검토한다.
- `Manager`는 조율자 역할만 한다. 계산, 표시, 데이터 정의를 붙이지 않는다.

## 4. Unity 역할 분리

- `MonoBehaviour`는 Unity 생명주기, 참조 연결, 이벤트 연결만 담당한다.
- 계산 로직은 순수 C# class로 분리한다.
- UI는 상태를 보여주고 버튼 이벤트를 전달한다.
- 전투 계산, 보상 계산, 생산 계산, 전투력 계산은 UI에서 하지 않는다.
- 저장 데이터와 임시 UI 상태를 섞지 않는다.

## 5. UI 규칙

- 화면마다 `new Color(...)`, `fontSize`, `height`를 직접 박지 않는다.
- 공통 UI 생성은 `HudUiFactory` 계열로 모은다.
- 공통 레이아웃 수치는 `HudLayoutConfig` 계열로 모은다.
- 에디터에서 직접 조절해야 하는 레이아웃 수치는 `ScriptableObject`나 Prefab으로 노출한다.
- 사용자가 직접 크기와 배치를 조절해야 하는 UI는 Prefab 기반으로 만든다.
- Prefab에서 색상과 텍스트 크기를 관리하는 UI에는 `HudPrefabStyleLock`을 붙여 코드가 스타일을 덮어쓰지 않게 한다.
- 고정 구획이 필요한 화면에서는 `FlexibleHeight`, `FlexibleWidth`를 남용하지 않는다.
- `LayoutRebuilder.ForceRebuildLayoutImmediate()`는 예외 상황에서만 쓴다.
- 보이는 화면만 갱신한다.
- 카드 목록은 가능하면 재사용한다. 매 갱신마다 전체 삭제 후 재생성하는 방식을 기본값으로 두지 않는다.

## 6. 편성 화면 규칙

- 헤더 아래에서 가능한 한 화면 상단까지 크게 쓴다.
- 프리셋 버튼, 액션 버튼, 하위 탭은 고정 크기로 둔다.
- 영웅 목록 영역이 남은 공간을 가져간다.
- 프리셋 버튼과 하단 버튼은 flexible에 의존하지 않는다.
- 빈 영웅 슬롯과 빈 룬 슬롯은 평소 클릭 이벤트를 갖지 않는다.
- 선택은 전역 성장축이므로 편성 슬롯이나 액션 대기 상태를 만들지 않는다.
- 편성 변경 저장 확인이 필요한 기능은 dirty state를 명확히 관리한다.

## 7. 전투 규칙

- `BattleManager`는 전투 루프 조율만 담당한다.
- 타겟 선정은 `CombatTargetingService` 같은 전용 서비스로 분리한다.
- 데미지 계산은 `CombatDamageService` 같은 전용 서비스로 분리한다.
- 몬스터 스폰은 `MonsterSpawnService` 같은 전용 서비스로 분리한다.
- 요새 전투는 `FortressCombatService` 같은 전용 서비스로 분리한다.
- 전투 렌더링은 전투 계산을 바꾸지 않는다.
- 스프라이트 시트는 전체 이미지를 직접 표시하지 말고, 명시적인 프레임 단위로 잘라서 표시한다.
- 공격, 이동, 피격, 사망 연출은 상태와 수명 값을 분리해서 관리한다.
- 전투 서비스는 UI 텍스트, 버튼, 패널을 참조하지 않는다.

## 8. 데이터와 밸런스 규칙

- 계산은 숫자로 하고 표시는 `NumberFormatter`에서 처리한다.
- 밸런스 수치는 코드 곳곳에 직접 넣지 말고 `GameData`, `Definition`, 데이터 테이블 계열에 둔다.
- 비용 공식, 확률 공식, 보상 공식은 버튼 클릭 핸들러에 직접 넣지 않는다.
- 장기 운영 성장 수치는 과한 퍼센트 보너스를 피한다.
- 보유 효과, 특성, 토템, 룬, 시설 보너스는 서로 곱연산이 누적되므로 총합 기준으로 검토한다.

## 9. 저장 규칙

- 저장 키는 `SaveKeys`에서만 정의한다.
- 저장 구조를 바꾸면 마이그레이션 가능성을 검토한다.
- 즉시 저장 기능과 저장 확인 기능을 섞지 않는다.
- 편성처럼 확인 팝업이 필요한 변경은 임시 상태와 저장 상태를 분리한다.

## 10. 한글과 인코딩

- C#과 문서는 UTF-8로 유지한다.
- `\uXXXX` 형태로 한글을 이스케이프해서 남기지 않는다.
- 한글 깨짐 문자가 보이면 기능 작업보다 먼저 복구한다.

## 11. 검증 규칙

작업 후 기본 검증:

- Unity C# 컴파일.
- 한글 깨짐 검사.
- 관련 화면 수동 확인.

리팩토링 후 추가 검증:

- public 동작이 바뀌지 않았는지 확인한다.
- 삭제한 코드가 실제 미사용인지 검색으로 확인한다.
- 파일 이동 시 namespace와 `.meta` 파일을 확인한다.

## 12. 현재 우선순위

현재 구조에서 가장 위험한 부분은 UI 레이아웃, 전투 렌더링, 거대 클래스다.

우선순위:

1. `GameHud`에 새 기능 직접 추가 금지.
2. `BattleManager`에 전투 기능 직접 추가 금지.
3. 편성 화면은 고정 구획 기반으로 유지.
4. UI 공통 factory/style/config 유지.
5. 보이는 탭만 refresh하도록 갱신 루트 축소.
6. 영웅 목록 카드는 재사용 구조 유지.
